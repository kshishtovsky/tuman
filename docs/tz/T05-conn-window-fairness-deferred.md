# Т05 — окно соединения: справедливость между потоками (ОТЛОЖЕНО, решение зафиксировано)

**Severity:** Medium в теории, Low на практике
**Репозиторий:** `E:/pet/tuman`
**Статус:** НЕ реализуется в этой итерации. ТЗ фиксирует решение и его причину,
чтобы вопрос не поднимался заново.

## Что не так

`mux/stream.go:273-284` (`reserve`) + `mux/mux.go:582` (`connWin`): окно
соединения 32 МиБ общее, а поток может взять до `winStream = 8 МиБ`. Один
bulk-поток (загрузка файла) занимает 25 % окна соединения, остальные потоки
ждут на `connWait` → Head-of-Line на уровне сессии.

## Почему не чиним сейчас

1. Справедливость требует согласованного поведения обеих сторон: квота
   `connWin / активных_потоков` должна учитываться и отправителем, и
   получателем, иначе получатель просто отвергнет данные (`ErrProtocol`),
   которые отправитель считает законными.
2. Изменение протокола = новая версия поведения; старый парк клиентов/серверов
   должен продолжать работать, значит нужен ещё и capability-флаг в AUTH_OK —
   это уже вторая итерация после Т03.
3. Эффект достижим без изменения протокола: пул из N независимых TLS-сессий
   (`client/client.go:32-34`, дефолт 4, максимум 2 на ендпоинт) уже разводит
   потоки round-robin (`client/pool.go:132-150`). Крупный поток упирается в
   одну сессию, остальные идут через другие.

## Что делать вместо

- Эксплуатационно: `Conns` = 2 × число ендпоинтов при агрессивных загрузках.
- Если появятся замеры, где один поток душит остальные внутри одной сессии —
  вернуться к ТЗ: квота в `reserve` + флаг `caps` bit 3 в AUTH_OK
  (`proto/auth.go:118-131`, `docs/07-proto-v1-spec.md:91-93`).

## Критерий возврата к задаче

Появление жалобы «один поток душит все» при `Conns ≥ 4`, подтверждённой
замером `tcpFlows`/`connWait` в логах `mux`.
