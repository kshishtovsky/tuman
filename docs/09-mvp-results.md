# 09. Результаты MVP: протокол и mux (этап 2, часть 1)

Дата: 28.10.2026. Ветка: `exp/tmn`. Задача: доказать, что свой слой поверх TLS не съедает скорость.

## 1. Что измерено

| Тест | Результат | Условия |
|---|---|---|
| `BenchmarkFrameRoundtrip` | 36.5 ns/op, **0 allocs/op** | заголовок 8 Б + payload, в памяти |
| `BenchmarkMarshalHeader` | 0.73 ns/op, 0 allocs | — |
| mux через `net.Pipe`, 64 МБ | 684 MB/s (5.5 Gbit/s) | Go-канал, не сеть |
| **mux через настоящий TLS 1.3 поверх TCP loopback, 256 МБ, 1 поток** | **1088 MB/s = 8.7 Gbit/s payload** | `mux/tlsbench_test.go` |
| 8 потоков параллельно по 4 МБ | все прошли, ошибок нет | — |
| Отказ при неверном PSK | отклонён (EOF), соединение не падает | — |
| TLS echo на 1 ядре VPS (без mux) | 337 MB/s (2.7 Gbit/s) | `docs/05` |

## 2. Вывод

**Запас по CPU и по стеку — 10× против цели 800 Мбит/с (= 100 МБ/с).** Настоящий TLS оказался даже быстрее `net.Pipe` (1088 против 684 MB/s) — то есть опасение «на сокете будет хуже» не подтвердилось.

Даже на одном ядре VPS, где TLS-echo даёт 337 MB/s, mux-путь укладывается с 3.4× запасом. Значит узкое место MVP — **только маршрут** (117–248 Мбит/с до текущего VPS), а не наш код.

## 3. Что это значит для плана

1. Переписывать mux на Rust или оптимизировать кадрирование **не нужно** — CPU не лимит.
2. Все усилия этапа 3 идут в: маршрут (другой хостинг), шейпер (форма трафика), anti-probing (фолбэк на сайт).
3. Требование владельца «скорость интернета терять нельзя» выполнено на уровне протокола с большим запасом; осталось проверить на живом канале.

## 4. Ограничения замеров

- Loopback: оба конца на одной машине (32 потока), реальный RTT = 0. На канале 55 мс добавятся BDP-эффекты — они лежат в TCP/BDP, а не в mux.
- Не измерено: поведение при 2 % потерь, паддинг-оверхед (этап 3), CPU на Android.
- Числа дают верхнюю границу; на живом VPS ожидается 60–90 % от них.

# 10. End-to-end: туннель собран и проверен (28.10.2026, вечер)

## 10.1 Что запущено

`tmns` (сервер) + `tmnc` (клиент, SOCKS5 на 127.0.0.1:11080) на одной машине, TLS 1.3, самоподписанный серт, PSK 32 байта.

## 10.2 Результаты живого прогона

| Проверка | Результат |
|---|---|
| Сайт-прикрытие: `GET /` | 200, 5035 байт, `Content-Length`/`Content-Type`/HSTS/nosniff/XFO, **без заголовка `Server`** |
| Сайт-прикрытие: `GET /nope` | 404, 1290 байт |
| Невалидный PSK / чужой exporter | соединение НЕ рвётся: отдаётся HTTP-ответ, ни TLS alert, ни RST |
| HTTPS через туннель (`example.com`) | 10 запросов подряд: **10/10 → 200**, тело 577 байт в каждом |
| Разные сайты (example.com, cloudflare, google, ifconfig.me) | 200, TLS 1.3 внутри потока проходит |
| Параллельно 4 потока в одной сессии | все 200, ошибок нет |
| Reconnect после рестарта сервера | backoff 1→2→4→8 с, новая сессия, старые потоки закрыты корректно |
| Скорость: 20 МБ через туннель vs напрямую | 86 vs 94 Мбит/с в одном прогоне; далее разброс 8–94 у обеих веток |

## 10.3 Найденный и исправленный баг (важный)

**SOCKS5 ATYP ≠ адресный блок нашего протокола.** В SOCKS5: 1=IPv4, **3=DOMAIN**, 4=IPv6. В TMN/1: 1=IPv4, 2=domain, 3=IPv6. Код клиента использовал константы протокола для разбора SOCKS-запроса, поэтому любой домен (`example.com`) читался как 16-байтовый IPv6-адрес, и CONNECT висел до таймаута 10 с. Лечилось только руками: тесты этого не ловили, потому что тестовый SOCKS-клиент использовал те же неверные константы. Добавлен регресс-тест.

Урок: любые внешние протоколы (SOCKS, HTTP) получают собственные константы, никакого переиспользования внутренних enum.

## 10.4 Про скорость: почему цифры шумные

Замер шёл в цепочке `tmnc → tmns → TUN rupas → VPS Хельсинки → сайт`, то есть двойное туннелирование, и egress-IP был `45.67.202.247`. Разброс 8–94 Мбит/с у обеих веток (и у прямой) означает, что узкое место — внешний канал, а не наш протокол. Корректный замер оверхеда требует отключённого TUN либо запуска `tmns` на удалённом хосте.

Что уже известно точно: mux+TLS на loopback = 8.7 Гбит/с, кадр = 36 ns / 0 allocs. Оверхед кадрирования (1400 Б payload при MSS ~1448) — максимум 3.3 %.
