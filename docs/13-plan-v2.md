# TMN/2: видение, требования и план работ

Дата: 2026-11-02. Основание: аудит `docs/12-security-audit.md`, PRD `docs/02-prd.md`,
SDD `docs/03-system-design.md`, `docs/10-stage3-decomposition.md`.

## 1. Видение

Сегодня TMN/1 — быстрый туннель с сайтом-прикрытием, который снаружи выглядит как
**Go-клиент с наклейкой `h2`**: стоковый ClientHello (3 шифра, 11 расширений, без
GREASE), 4 TLS к одной паре (IP,SNI) за 13 мс, бинарный кадр первым байтом после
согласованного `h2`, адреса целей в логах сервера. Скорость у него есть (227 Мбит/с
на живой маршрут, 335 МБ/с mux на 32 потоках, 0 аллокаций на кадр), а вот обещание
«неотличим от браузера» не выполняется ни в одной части: ни отпечаток, ни профиль
соединений, ни логи.

TMN/2 — это тот же быстрый кадровый туннель, у которого:

1. **Снаружи нет ни одного признака, отличающего его от визита в браузере** —
   отпечаток Chrome, профиль соединений ≤2 на ендпоинт, ALPN соответствует
   содержимому, логи без целей.
2. **Внутри нет доверия ни одной из сторон по умолчанию** — обе доказывают знание
   ключа, реплей невозможен, нарушитель окна убивает только себя.
3. **Сбой одного компонента не убивает остальное** — поток не роняет сессию, сессия
   не роняет сервер, сервер не роняет процесс.

Целевой пользователь — 1–5 человек на своём VPS (G6 PRD), владелец сам себе админ.
Отсюда приоритет: не «фичи для рынка», а **отсутствие поводов заметить нас и
отсутствие способа уронить сервис**.

## 2. Требования TMN/2

Метки: **R** — обязательное для v2, **O** — желательное.

### Безопасность

| ID | Требование | Приёмка |
|---|---|---|
| R-SEC-1 | Сервер доказывает знание PSK в `AUTH_OK` (MAC + эхо nonce) | фейк-сервер без PSK не устанавливает сессию: `mux.New(IsClient:true)` возвращает ошибку |
| R-SEC-2 | Привязка AUTH не зависит от TLS-стека | AUTH проходит под `utls.HelloChrome_Auto` и под `crypto/tls` одинаково |
| R-SEC-3 | Реплей AUTH невозможен в пределах окна | повтор `(ts,nonce)` на другой сессии → `ErrAuth`; кэш один на сервер, под `-race` |
| R-SEC-4 | Egress ограничен политикой: никаких loopback/RFC1918/link-local/metadata | диал на `127.0.0.1`, `169.254.169.254`, `10.0.0.1`, `::1` отклоняется до соединения |
| R-SEC-5 | В логах нет SNI, адресов и URL целей | грепом по debug-логу потока не находится ни одного `host:port` цели |
| R-SEC-6 | Приёмное окно соблюдается принудительно | пир, заливший > окна, теряет сессию; RSS сервера не растёт |
| R-SEC-7 | Окно свежести `ts` не обходится переполнением | `ts = now ± 2^63` → `ErrAuth` |
| R-SEC-8 | Права PSK-файла проверяются (не-Windows) | файл 0644 → отказ на старте |

### Устойчивость

| ID | Требование | Приёмка |
|---|---|---|
| R-RES-1 | Ошибка уровня потока не роняет сессию | дубль OPEN, DATA после FIN, 257-й OPEN в accept → закрыт только поток |
| R-RES-2 | Исчерпание stream id не превращает туннель в зомби | `ErrExhausted` → пул переподключает сессию |
| R-RES-3 | `WU` с любой дельтой не вешает и не раздувает окно | `WU(2^31)`, `WU(2^32-1)` — окно в границах, `Write` не виснет |
| R-RES-4 | Флуд не выедает CPU до handshake | соединение сверх лимита закрывается до TLS; ошибка `Accept` не роняет процесс |
| R-RES-5 | Обрыв сразу после установления не даёт лавину | ≤2 реконнекта/с на ендпоинт при сервере, рвущем сразу |
| R-RES-6 | Восстановление после блипа ≤3 с (NFR-12) | сервер вернулся → 4 сессии за ≤3 с |
| R-RES-7 | `Close()` не виснет на conn без `io.Closer` | `Close()` возвращается < 3 с |
| R-RES-8 | relay не держит поток вечно | SOCKS-нога с idle > 300 с закрывается |

### Производительность и неотличимость

| ID | Требование | Приёмка |
|---|---|---|
| R-PERF-1 | Горячий путь остаётся zero-alloc | бенч `-benchmem`: аллокаций на кадр не больше, чем сейчас |
| R-PERF-2 | Mux не теряет скорость при контроле окна | `BenchmarkMuxThroughput` ≥ 600 МБ/с |
| R-PERF-3 | Отпечаток = браузер | JA3/JA4 совпадает с Chrome; ALPN соответствует первому байту |
| R-PERF-4 | Не более 2 TLS на ендпоинт | на одном ендпоинте при `conns=4` поднимается 2, не 4 |
| R-PERF-5 | Resumption включён | в hello присутствует ext 41, `DidResume=true` на втором коннекте |

## 3. AUTH v2 (R-SEC-1, R-SEC-2, R-SEC-3)

### Формат

```
AUTH     (клиент → сервер), 82 байта:
  ver      u16 = 2
  ts       u64  (unix, окно ±120 с, без модуля — сравнение в обе стороны)
  nonce    8    (случайный)
  clientPub 32  (X25519, эфемерный)
  tag      32   = HMAC-SHA256(psk, "TMN1-AUTH-V2" ‖ ver ‖ ts ‖ nonce ‖ clientPub)

AUTH_OK  (сервер → клиент), 74 байта:
  ver      u16 = 2
  nonce    8    (эхо из AUTH)
  serverPub 32  (X25519, эфемерный)
  tag      32   = HMAC-SHA256(psk, "TMN1-AUTH-OK-V2" ‖ clientPub ‖ serverPub ‖ ts ‖ nonce)

sessionKey = HKDF-SHA256(salt=psk, ikm=X25519(clientPriv, serverPub), info="TMN1-SESSION-V2", 32)
```

Всё фиксированной длины, big-endian, без negotiate: `ver != 2` → отказ (поверхности
downgrade нет, как и в v1).

### Почему ECDH вместо TLS-exporter

Exporter был выбран, чтобы привязать AUTH к конкретному TLS-соединению. Он это делает
корректно — но только на `crypto/tls`: браузерные ClientHello в uTLS включают
`renegotiation_info`, utls из него включает renegotiation, и exporter становится
недоступен (проверено, см. `12-security-audit.md` §5). Плюс exporter привязывает нас к
TLS, а на роадмапе QUIC — там своя обвязка.

X25519 внутри AUTH даёт то же свойство (сессионный ключ знают только двое) без
зависимости от транспорта и без доверия к TLS-стеку. Стоимость — одна пара ключей на
сессию (~50 мкс) и +32 байта в AUTH.

### Threat model

| Атака | До v2 | После v2 |
|---|---|---|
| MITM с доверенным CA читает трафик | видит цели и payload (S2) | получает `AUTH`, но не может ответить валидным `AUTH_OK` → клиент рвёт сессию до отправки целей |
| Реплей AUTH в пределах 120 с | невозможен (exporter), но и кэш мёртв | кэш на сервере + `ts` → `ErrAuth` |
| Реплей после 120 с | невозможен | невозможен (окно) |
| Подмена nonce/pub | n/a | тег ловит |
| Компрометация PSK | полный доступ | полный доступ (по-прежнему единственный секрет) |

Что v2 **не** решает: защиту от квантового противника (X25519 и HMAC — классика),
защиту от компрометации самого устройства клиента, сокрытие факта использования
туннеля от активного зонда, который знает протокол.

### Проверено (не теория)

`proto/auth.go` реализован и покрыт тестами, и дизайн проверен сквозным прогоном:
`uTLS` (HelloChrome_Auto / HelloFirefox_Auto / HelloSafari_Auto / HelloGolang) →
TLS 1.3 → AUTH v2 → AUTH_OK v2 → session key. Результат по всем четырём отпечаткам:

```
chrome   alpn="http/1.1" authok_verify=<nil> srv_err=<nil> key_match=true
firefox  alpn="http/1.1" authok_verify=<nil> srv_err=<nil> key_match=true
safari   alpn="http/1.1" authok_verify=<nil> srv_err=<nil> key_match=true
golang   alpn="http/1.1" authok_verify=<nil> srv_err=<nil> key_match=true
```

То есть браузерный отпечаток и взаимная аутентификация совместимы — чего нельзя было
сделать на TLS-exporter. Тесты `proto/auth_v2_test.go`: `TestAuthOKV2RequiresMAC`
(в т.ч. v1-подобный 12-байтовый AUTH_OK отвергается), `TestSessionKeyV2` (включая
low-order point), `TestAuthSkewOverflow` (доказывает, что старая формула давала
`d = -9223372036854775808` и пропускала метку), `TestReplayConcurrent` под `-race`.

### Миграция

Разрыв совместимости: старый клиент с новым сервером и наоборот не работают. Порядок:
сервер обновляется первым, но **не заменяет сетевой порт**, пока не обновлены клиенты —
на время перехода держим два listener'а (v1 на старом порту, v2 на новом), затем
v1 выключается. Бинарник v1 сохраняем для отката. В `docs/07-proto-v1-spec.md`
добавляется раздел «v2», старая спецификация остаётся как история.

## 6. Порядок и риски

Приоритет работ: S1 (OOM) → S3 (SSRF) → S4 (логи) → S2/S7 (AUTH v2 + uTLS) →
устойчивость клиента → всё остальное. Логика: сначала то, что превращает утечку ключа
или баг пира в компрометацию хоста; потом то, что видно снаружи; потом удобство.

Риски:

1. **Протокольный разрыв** (AUTH v2). Смягчение: двойной listener на время миграции +
   сохранённый v1-бинарь.
2. **Контроль окна против скорости** (R-PERF-2). Смягчение: проверка перед `push` в том
   же критическом участке, что уже берётся под `s.mu`; бенч до/после обязателен.
3. **uTLS из локального кеша** — версия `v1.8.2` проверена, но сети до
   `proxy.golang.org` нет. Смягчение: сборка с build-tag, `crypto/tls` остаётся
   дефолтом, пока `go mod tidy` не пройдёт на машине с сетью.
4. **Правки четырёх агентов в одном рабочем дереве** без коммитов. Смягчение: файловые
   наборы не пересекаются, я проверяю каждую правку и гоняю полный `go test ./...`
   после сведения.
5. **Всё измерено на loopback.** Живой DPI, потери, смена сети — только на VPS.

| лавина реконнектов | `client/pool.go` | 6 handshake за 4 с вместо 6189 за 3 с |
| восстановление после блипа | `client/health.go` | 511 мс (NFR-12 ≤ 3 с) |

Версия AUTH выбирается **по длине кадра** (`proto.AuthV2Len`), согласования нет —
старый клиент продолжает работать с новым сервером. Живьём: v1-бинарь `9db9287`
против нового сервера — 2.0 МБ за 0.97 с; `auth_v2=true` — 2.0 МБ за 0.95 с.

**Найдено при сведении (не в отчётах агентов):**

1. Агент сузил ALPN сервера до `["http/1.1"]`, а клиент просил `h2` — старый парк
   перестал подключаться (`handshake` падал на ALPN). Сервер: `http/1.1` первым,
   `h2` вторым; клиент предлагает `h2,http/1.1` (как браузер). В TLS 1.3 выбор едет
   в EncryptedExtensions и пассивному DPI не виден, поэтому запрет `h2` ничего не давал.
2. **Первый запрос после старта клиента обрывается** — воспроизводится и на базе
   `9db9287`, к правкам не относится. Лечится прогревом пула, не сделано.
