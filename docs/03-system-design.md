# 03. System Design: TMN/1 — слой формы и диспетчеризации поверх TLS/QUIC

Версия 0.1 (этап 1). Вход: `01-research-dpi-2026.md`, `02-prd.md`.

---

## 0. Главное решение в одном абзаце

Мы **не изобретаем handshake и криптографию**. Внешний слой — настоящий TLS 1.3 с отпечатком реального браузера (uTLS) и настоящим сертификатом на своём домене, за которым стоит настоящий сайт-прикрытие. Внутри — собственный кадровый протокол (мультиплексирование, управление потоком, паддинг, миграция). Инновация — не в шифровании, а в **трёх вещах**: (1) целевой шейпинг профиля записей под эталон, а не случайный паддинг; (2) политика соединений и ASN, обходящая эвристики 2026 года; (3) сервер, который для неавторизованного клиента неотличим от обычного сайта. Это даёт 80 % эффекта при 20 % риска.

Причина отказа от «своего протокола с нуля»: любая новая сигнатура на L2 (формат первого пакета, длины, тайминги handshake) — это новая фингерпринт-мишень, которую ТСПУ выучит за недели, и при этом мы получим собственный класс крипто-багов. TLS 1.3 — единственный протокол, который цензор *обязан* пропускать в промышленных объёмах.

```
КЛИЕНТ (Win/Android)                              VPS ХЕЛЬСИНКИ
┌──────────────────────────────┐                ┌───────────────────────────────┐
│ приложения (браузер, Discord)│                │                               │
│        │ TUN / SOCKS5        │                │   :443/tcp  ── cover site     │
│  ┌─────▼──────────────────┐  │   TLS 1.3      │     (nginx, статика, серт)    │
│  │ Router / policy engine │  │  + HTTP/2|3    │        │ SNI/Host = наш домен │
│  │  (split, geo, per-app) │  │◄──────────────►│  ┌─────▼──────────────────┐   │
│  └─────┬──────────────────┘  │                │  │ tmn-server             │   │
│  ┌─────▼──────────────────┐  │                │  │  auth → mux → egress   │   │
│  │ TMN session (mux)      │  │                │  └─────┬──────────────────┘   │
│  │  streams, flow control │  │                │        │                      │
│  └─────┬──────────────────┘  │                │   ┌────▼─────┐  ┌───────────┐  │
│  ┌─────▼──────────────────┐  │                │   │ direct   │  │ WARP-like │  │
│  │ Shaper (профили, pacing)│ │                │   │ egress   │  │ egress    │  │
│  └─────┬──────────────────┘  │                │   └──────────┘  └───────────┘  │
│  ┌─────▼──────────────────┐  │                │                               │
│  │ Cover: uTLS / uQUIC    │  │                │  :443/udp — QUIC-режим (опция)│
│  └────────────────────────┘  │                └───────────────────────────────┘
└──────────────────────────────┘
        health / endpoints ──► control plane (конфиг, подписка, ротация)
```

Компоненты и их ответственность:
1. **Router**: решает, что идёт напрямую, что в туннель, что вообще блокируется. Правила: домены/geoip/приложение/порт.
2. **Session**: одна логическая сессия на ендпоинт (см. §6), мультиплексирование потоков, окна, keepalive.
3. **Shaper**: превращает поток кадров в последовательность записей нужных размеров и таймингов.
4. **Cover**: TLS 1.3 (uTLS Chrome/Safari/Firefox по профилю) или QUIC v1 (uQUIC), ALPN `h2`/`h3`.
5. **Server**: при валидном ключе — прокси; при невалидном — обычный веб-сервер (это и есть anti-probing).

## 2. Протокол TMN/1

### 2.1 Два режима инкапсуляции

| Режим | Что снаружи | Когда | Цена |
|---|---|---|---|
| **WEB** (по умолчанию) | HTTP/2 или HTTP/3: настоящие запросы к путям сайта, наши кадры внутри DATA | всегда, если не доказано обратное | оверхед framing ~1–3 %, сложность |
| **RAW** | сразу AEAD-кадры после TLS handshake, без HTTP-семантики | bulk-загрузки, длинные сессии, где HTTP-мимикрия не даёт ничего | выше риск по L4, нет «бесплатной» легенды |

RAW не является «скрытым режимом по умолчанию»: он выбирается политикой и только после того, как WEB отработал handshake (то есть снаружи всё равно виден обычный TLS-визит).

### 2.2 Handshake

1. TCP (или UDP для QUIC) → TLS 1.3, uTLS-отпечаток из профиля. SNI = наш домен. Сертификат настоящий (Let's Encrypt / ZeroSSL), сайт-прикрытие отвечает реальным HTML.
2. Первый DATA-кадр: `AUTH` — тег `HMAC-SHA256(psk, "TMN1-AUTH" || tls_exporter || version || timestamp || nonce)`, `timestamp` ±120 с, `nonce` 8 байт, счётчик replay. Фактический формат — `docs/07` §4 и `proto/auth.go`; `client_random` заменён на TLS exporter, потому что `tls.ConnectionState` его не отдаёт.
3. Сервер при валидном AUTH отвечает `AUTH_OK` + версия + список возможностей (типы кадров, размер окна, поддержка миграции).
4. При невалидном AUTH сервер **не отвечает ошибкой протокола**: соединение продолжает жить как обычный HTTPS-визит (отдаётся сайт). Никаких RST, TLS alert, нестандартных кодов — это главное отличие от наивных прокси.
5. Resumption: TLS session ticket + PSK-токен → 0-RTT для `AUTH` следующей сессии (только для идемпотентных первых кадров; bulk-потоки стартуют после 1-RTT).

### 2.3 Кадр

Фиксированный 8-байтовый заголовок (zero-alloc парсинг, без varint в hot path):

```
 0       1       2-3        4-5        6-7
+-------+-------+----------+----------+----------+
| type  | flags | stream   | length   |  reserved|
+-------+-------+----------+----------+----------+
payload: length байт (≤ 1400 в WEB, ≤ 1350 в QUIC)
```

Типы: `DATA 0x01`, `ACK 0x02` (для DATAGRAM-потоков), `PAD 0x03`, `PING 0x04`, `WU 0x05` (window update), `FIN 0x06`, `MIG 0x07` (миграция/смена пути), `AUTH 0x08`, `AUTH_OK 0x09`, `CLOSE 0x0A`.

Флаги: `FIN`, `MORE` (продолжение сообщения), `URGENT` (голос/интерактив — идёт вне очереди шейпера).

Семантика потоков:
- `stream` — u16: 0 — управление, 1..N — логические потоки (клиент **нечётные** 1,3,5…, сервер **чётные** 2,4,6…; см. `mux/mux.go`: `nextID` клиента = 1, сервера = 2).
- TCP-поток: байтовый поток + окна.
- UDP-поток (голос, игры): `DATA` + `ACK`, потерянные кадры не переотправляются (или переотправляются только в режиме `reliable=1`), размер окна 64 КБ, TTL 400 мс — чтобы не копить задержку.

### 2.4 Управление потоком

- Окно на поток и на соединение. Старт 4 МБ, автоподстройка под `2 × BDP` (нужно для 800 Мбит/с при RTT 30 мс: BDP = 3.75 МБ).
- `WU` шлётся при потреблении 25 % окна (не на каждый кадр — иначе шторм мелких кадров и «палевный» профиль).
- Мёртвая зона: не дробить поток на кадры меньше 1 КБ, кроме интерактива (коалесинг 1–2 мс).

### 2.5 Что не делаем

- Не изобретаем CC: TCP — ядерный BBR, QUIC — BBRv3 из quic-go. Свой CC = своя деградация на 1 Гбит/с.
- Не изобретаем AEAD: AES-128-GCM (AES-NI) с ключами из TLS exporter; ChaCha20 только если нет AES-NI.
- Не делаем «свой TLS» (GREASE-паттерны, расширения): uTLS берёт настоящий браузерный.

## 3. Shaper: целевой шейпинг вместо случайного паддинга

### 3.1 Задача
Сделать распределение `(размер записи, интервал)` похожим на выбранный эталон. Не «случайный шум» (он сам является сигнатурой — равномерный паддинг отличается от любого реального профиля), а **подгонка под конкретный класс трафика**.

### 3.2 Профили

| Профиль | Эталон | Когда |
|---|---|---|
| `browse` | HTTP/2 к обычному сайту: мелкие записи 200–1500 Б, паузы 50–800 мс, всплески | браузинг, API |
| `video` | сегментированный видеопоток: устойчивые 1–1.4 КБ записи, ровный pacing | YouTube/стриминг |
| `bulk` | крупное скачивание: только крупные записи, минимум паддинга | загрузки > 50 МБ |
| `voice` | WebRTC/DTLS-SRTP: маленькие частые датаграммы 80–1200 Б, 20 мс каденция | Discord/SIP |

### 3.3 Правила (важное решение)
- **Паддинг включается там, где он окупается.** Первые 64 КБ сессии и все «мелкие» фазы — pad до распределения эталона. Устойчивый bulk — без паддинга (иначе 800 Мбит/с превращаются в 500 без выигрыша: детект bulk-объёма всё равно идёт по длительности и объёму, а не по размерам записей).
- Жёсткий потолок паддинга: ≤ 20 % полосы, ≤ 2× размера полезной нагрузки на запись.
- **Запрет одиночных мелких записей** в начале сессии: любая запись < 700 Б коалесится или добивается — это прямой ответ на TLS-in-TLS детект по размеру первого ClientHello-подобного блока.
- Джиттер интервалов: не более ±3 мс на 20 мс каденции для `voice` (иначе растёт jitter и портится голос).
- `URGENT`-кадры обходят шейпер (задержка важнее формы).

### 3.4 Как проверяем «похожесть»
Оффлайн: захват 10 минут эталона, сравнение распределений (KS-тест по размерам, energy distance по интервалам), порог — «не отличить на 10k записей при p<0.01». Онлайн: эмулятор DPI (§8) ставит балл подозрительности.

## 4. Сервер: поведение под активным зондированием

| Проба цензора | Что видит сервер |
|---|---|
| TLS handshake с нашим SNI | настоящий серт, HTTP/2, отдаётся сайт-прикрытие |
| HTTP GET / | 200, HTML, заголовки как у nginx |
| GET /произвольный путь | 404 как у обычного сайта |
| невалидный AUTH | продолжается обычный HTTPS-обмен, без ошибок протокола |
| повторное соединение с тем же AUTH/replay | соединение принимается как обычное, ключ не используется |
| TLS с чужим SNI (SNI-fronting) | сервер отвечает своим сертом; поведение — как у обычного сервера (нужен `default_server`) |
| много соединений с одного IP | rate-limit на уровне nginx, как у обычного сайта |

Дополнительно:
- Тайминг ответа на невалидный AUTH искусственно выравнивается (не «мгновенный RST» и не «молчание 30 с»).
- Никаких открытых портов, кроме 443 (+ 443/udp если QUIC), никакой панели на публичном IP (только через SSH/VPN).
- Логи: без SNI/URL/целевых адресов; только объёмы, RTT, коды ошибок.

## 5. Политика соединений и ASN (ответ на эвристики 2026)

Факты, под которые проектируем (июнь 2026, вторичные источники): параллельные TLS-соединения к одному ресурсу → заморозка ~2 мин; смена фингерпринта → до 10 мин.

**Поправка по первичным данным владельца (важнее литературы):** Reality + XHTTP на одном IP проработали больше года, до **~50 ГБ/сутки** через туннель, без блокировок. Значит порог «объём на адрес» на канале владельца заведомо выше, и лимиты ниже — это страховка, а не физика.

| Правило | Реализация | Умолчание (калибровка) |

| Правило | Реализация |
|---|---|
| Одна сессия на ендпоинт | мультиплексирование вместо пула; xmux-политика не более 2 соединений, и только при доказанном head-of-line блокировании |
| Один фингерпринт на сессию | фиксируется при старте, не меняется в пределах часа; смена — только при переподключении с новым IP/ендпоинтом |
| ASN-диверсификация | ≥ 2 ендпоинта в разных AS, ротация по объёму (например, каждые 20 ГБ) |
| Лимит объёма на адрес | суточный порог на IP — **телеметрия + мягкий триггер**, не жёсткий резак; при превышении сначала растёт частота health-check, потом ротация | 50 ГБ/сутки (полевой факт проходит), 150 ГБ — ротация |
| Разнесение up/down | опция `split-path`: аплоад через один ендпоинт, даунлоад через другой (сбивает корреляцию «один IP — 40 ГБ вниз») |
| Тайминг активности | keepalive раз в 25 с; **длительность сессии не ограничиваем** — годовой опыт владельца с длинными сессиями не показал реакции канала |

Плата: больше адресов, сложнее конфиг. Второй IP — не «потому что объем ловится», а потому что смена адреса должна занимать минуты, когда детект всё-таки включат. Приоритет: сначала качественный маршрут (`06-route-matrix.md`), потом второй адрес.

### 5a. Что мы честно не знаем

Детектируется ли конкретный профиль на канале владельца **сейчас** — неизвестно: год работы мог пройти потому, что ТСПУ не смотрел на этот ASN/класс, или смотрел и не смог. Различить эти гипотезы можно только активным экспериментом:

1. поднять наш транспорт рядом с работающим Reality на **том же** сервере;
2. гонять контролируемый объём (10/30/50 ГБ в сутки) и смотреть, не начнёт ли деградировать Reality — это и есть индикатор «нас заметили и связали с адресом»;
3. вести журнал: дата, объём, деградация, что делали.

Это дешевле, чем строить теорию, и даёт настоящие пороги вместо чужих статей.

## 6. Транспорты

### 6.1 TCP (основной)
- Настройки ядра на VPS: `net.ipv4.tcp_congestion_control=bbr`, `fq`, `tcp_rmem/wmem` до 16 МБ, `tcp_mtu_probing=1`, `tcp_notsent_lowat` для интерактива.
- Клиент: BBR недоступен на Windows → туннель всё равно выигрывает, потому что узкое место — не клиентский CC, а внешний канал; проверка `[ЗАМЕР]`.
- Zero-copy: на Linux-сервере — `splice()` между сокетами там, где нет необходимости перешифровывать; в Go это делается только на `net.TCPConn` (не через `tls.Conn`). Практический вывод: RAW-режим с переупаковкой кадров, а не Vision-splice.
- Быстрый режим (Vision-подобный splice) — через существующий Xray как отдельный профиль «если скорость важнее незаметности», не пишем сами.

### 6.2 QUIC (ускорение на потерях, мобильный)
- `quic-go` + uQUIC-отпечаток Chrome, ALPN `h3`, Initial padding до 1200 Б (как у всех), миграция по connection ID.
- CC: BBRv3, `MaxDatagramFrameSize` для голоса.
- Ограничение: если UDP режут/троттлят — QUIC отключается автоматически (health-check по потере первых пакетов), голос едет по TCP-пути с оговоркой по jitter.

### 6.3 Лестница фолбэков
```
1. TCP/TLS + WEB (наш домен)         — базовый
2. TCP/TLS + RAW                     — если HTTP-мимикрия мешает скорости
3. QUIC/443 + WEB                    — если TCP режут или высокие потери
4. TCP/TLS к другому ендпоинту (ASN) — если IP заблокирован
5. Xray Reality на резервном порту   — ручной «аварийный» профиль
6. SSH-туннель / zapret-стратегия    — последняя линия
```
Каждый шаг — автоматически по health-метрикам (RTT, доля потерь, время до первого байта, коды ошибок), с журналом «почему переключились» (FR-11).

## 7. Производительность: бюджет 800 Мбит/с

Измерено на машине разработчика (Go 1.26.5, 32 ядра):
```
AES-256-GCM, 1 поток ............ 6.83 GB/s (54.7 Gbit/s)
TLS 1.3 echo, 16 КБ чанк ........ 766 MB/s payload (6.13 Gbit/s)
```
Расход на 800 Мбит/с (= 100 МБ/с):
- AEAD: ~1.5 % ядра на одну операцию; с двойным шифрованием — ~3 %.
- Полный TLS-путь клиента: ~13 % того, что даёт loopback-бенчмарк.
- Реальные издержки: syscalls, копии, паддинг (до 20 % полосы), HTTP/2 framing (1–3 %).
- Ожидание: 700–850 Мбит/с на одном потоке при исправном VPS; узкое место — канал VPS, а не CPU. `[ЗАМЕР]` после стенда.

Правила инженерии, чтобы это не потерять:
- пулы буферов, никаких аллокаций в hot path (`sync.Pool`, `[]byte` фиксированных классов);
- батчинг записей (coalescing 1–2 мс) — снижает syscall/packet rate с 69k pps до единиц тысяч;
- `TCP_NODELAY` + `tcp_notsent_lowat` для интерактива, но батчинг для bulk;
- GSO/GRO на сервере (Linux), `SO_REUSEPORT` для нескольких воркеров;
- шейпер не должен вносить задержку в `URGENT`.

## 8. Тестовая стратегия (детали — `04-lab-plan.md`)

Стенд: Linux-контейнер с `NET_ADMIN` + `netns` + `tc netem` (RTT 30 мс, потери 0–2 %) + эмулятор DPI на nfqueue с правилами:
1. сигнатура WG/SS/OpenVPN (регексп по первым байтам);
2. JA3-белый список браузеров;
3. TLS-in-TLS: запись < 700 Б в первых 4 КБ после handshake + паттерн «малая запись → крупный ответ»;
4. поведение: > 3 параллельных TLS к одному (IP, SNI) за 60 с → заморозка 120 с;
5. шейпинг: доля UDP > X % от полосы → троттлинг до 5 Мбит/с.

DoD этапа 1: 5 правил воспроизводятся, 3 кандидата (наш WEB, XHTTP, Reality) прогнаны, цифры в таблице, решение по v1 зафиксировано.

## 9. Безопасность

| Угроза | Митигация | Остаточный риск |
|---|---|---|
| Пассивный анализ | TLS 1.3, ECH не нужен, паддинг/шейпинг | остаются объём и длительность |
| Активное зондирование | сайт-прикрытие, нет ошибок протокола, выравненный тайминг | целевое зондирование с валидным ключом (утечка конфига) |
| Replay | timestamp ±120 с + счётчик `(ts, nonce)` в LRU | окно replay 120 с. В v1 счётчик был мёртв (создавался на сессию, где AUTH один); в v2 — один кэш на сервер (`proto.NewReplayCache`) |
| Кража конфига/подписки | ключи в OS keychain, подписка подписью Ed25519, ротация | компрометация устройства |
| DoS/амплификация | нет UDP-ответов без AUTH, rate-limit | обычный флуд |
| Утечка DNS | DoH внутри туннеля, блок утечек | — |
| Перехват TLS (сертификаты Минцифры) | внутренний TLS до сайта не трогаем, наш слой — второй | MITM видит только наш шифротекст |
| Логи | нет логирования адресов/URL | — |

## 10. Развёртывание (Хельсинки)

```
VPS (Хельсинки)
├── 443/tcp  : tmn-server (TLS, наш домен, сайт-прикрытие)
├── 443/udp  : tmn-server QUIC  (или отдельный порт, если 443/udp занят Hysteria2)
├── 8443/tcp : существующая панель (только localhost / SSH-туннель)
└── 22/tcp   : SSH (ключ, fail2ban, без пароля)
```
- Панель и текущие профили (Reality/XHTTP/Hysteria2) не трогаем — новый демон ставится рядом (FR-13).
- Второй ендпоинт: другой провайдер/ASN, тот же домен (или второй поддомен), тот же серт (wildcard)
- Мониторинг: локальный экспортер (RTT, throughput, retransmits, доля паддинга), алерт в Telegram при деградации.
- Обновления: бинарь + systemd unit, без автообновления из сети.

## 11. Альтернативы и почему отвергнуты

| Вариант | Почему нет |
|---|---|
| Свой крипто-протокол (свой handshake, свой Noise-профиль) | новая сигнатура + свой класс багов; L3 и так закрывается настоящим TLS |
| Только Reality | ASN-дыра, поведение, волны 2026; оставляем как резерв |
| Только XHTTP | нет целевого шейпинга и политики соединений; HTTP/2 оверхед |
| Только Hysteria2 | UDP режут; брутальный CC = «bulk UDP» |
| MASQUE (CONNECT-IP/UDP, RFC 9484) | правильный стандарт, но выдаёт себя по H3-профилю и требует своего стека; кандидат на этап 4 |
| Mieru-подход (без TLS, паддинг) | нет легенды «обычный сайт», значит активное зондирование убивает |
| Conjure/refraction | требует сотрудничества ISP — недоступно |
| Snowflake | низкая скорость и высокий jitter — не для 800 Мбит/с |
