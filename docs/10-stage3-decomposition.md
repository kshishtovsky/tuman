### T3.1 `feat/shaper` — шейпер формы трафика

**Зачем.** Сейчас мы гоняем кадры как есть: плотный поток записей ≤1400 Б — ровно та форма, которой ТСПУ ловит TLS-in-TLS. Нужно привести форму к профилю реальной нагрузки.

**Где шов.** `mux` пишет в `conn io.ReadWriter`. Шейпер — обёртка над TLS-соединением, которую передаём в `mux.New()` вместо самого conn. `mux` **не меняется вообще**. Это важно: не трогать `mux/`, иначе конфликт с другими ветками.

**Что сделать:**
- `shaper/` — пакет: `New(inner io.ReadWriter, cfg Config) *Shaper`, реализует `io.ReadWriter`.
- Профили: `browse` (мелкие записи 200–1500 Б, паузы, всплески), `video` (ровный поток 1–1.4 КБ), `bulk` (крупные, без паддинга), `voice` (каденция 20 мс), `off` (пропуск как есть).
- Правила из SDD §3.3: паддинг только в первые N КБ сессии и в мелких фазах; потолок паддинга ≤20 % полосы и ≤2× полезной нагрузки на запись; запрет одиночных записей <700 Б в начале сессии (коалесинг); `URGENT`-кадры обходят шейпер; для `voice` джиттер ≤3 мс.
- Pacing: разнос отправки по времени, но без добавления задержки в `URGENT`.
- Конфиг: `profile = off|browse|video|bulk|voice` в tmns.toml и tmnc.toml, по умолчанию `off` (чтобы не ломать замеры этапа 2).
- Тесты: распределение размеров на выходе соответствует профилю (KS-тест или просто границы), паддинг не превышает потолок, `URGENT` проходит без задержки, `io.Copy` через шейпер не теряет байты и не аллоцирует в hot path.

**DoD:** `go test ./shaper/ -race` зелёный; бенчмарк показывает оверхед паддинга; `mux/` и `cmd/` не изменены (кроме конфиг-поля в cmd — см. ниже).

**Проводка:** поле `profile` в конфигах и передача `shaper.New(...)` в `mux.New(...)` — делает **T3.1** в `cmd/tmns/main.go` и `cmd/tmns/server.go` (там где создаётся mux) и в `cmd/tmnc/main.go` (функция `dial`). Ветки `endpoint` и `route` тоже трогают эти файлы — координата конфликта указана в §«Конфликты».

### T3.2 `feat/route` — split-tunnel по правилам

**Зачем.** Игры и РФ-сайты не должны идти через Хельсинки: туннель добавляет 55 мс. FR-2.

**Что сделать:**
- `route/` пакет: правила `Action ∈ {Direct, Tunnel, Block}`; сопоставление по домену (suffix/glob), CIDR (IPv4/IPv6), порту.
- Формат правил: `routes.toml` или встроенные списки. Минимум: список RU-доменов/подсетей (можно компактный, 100–500 записей, не 200k) + правило по умолчанию `tunnel`.
- Кеш решений (домен → действие) с TTL, без утечек памяти.
- В клиенте: `cmd/tmnc/socks.go` — в `handle()` после `negotiate` спросить `route.Decide(host, port)`; при `Direct` — `net.Dial` напрямую и обычный relay, без открытия потока в mux. При `Tunnel` — как сейчас.
- Тесты: правила (suffix, CIDR, порт, приоритет), кеш, `Decide` не аллоцирует на горячем пути, direct-путь работает end-to-end (SOCKS5 → прямой эхо-сервер, сессия не создаётся).
- Конфиг: `routes_file = "..."` в tmnc.toml, по умолчанию пусто → всё в туннель.

**DoD:** `go test ./route/ ./cmd/tmnc/ -race` зелёный; поведение по умолчанию не изменилось (пустой конфиг = всё в туннель).

### T3.3 `feat/endpoint` — мультиендпоинт, health, отказоустойчивость

**Зачем.** Один адрес = одна точка отказа. Нужно ≥2 ендпоинта и автопереключение без действий руками (G3: восстановление ≤60 с).

**Что сделать** (только `cmd/tmnc/main.go` и новый `cmd/tmnc/health.go`):
- Конфиг: `servers = ["host:port", ...]` (вместо/вместе с `server`), `conns` на каждый сервер суммарно.
- Health: per-endpoint счётчики (успешные dial, ошибки, время до первого байта), простой score; при провале — не подключаться N секунд (cooldown), пробовать следующий.
- `connector` получает список ендпоинтов и раскидывает слоты пула по ним (например 4 conns = 2+2 по двум серверам).
- Лог: причина переключения без адресов (только индекс ендпоинта).
- Тесты: падение одного ендпоинта → потоки идут через второй; возврат первого после cooldown; пул распределён по серверам; счётчики health корректны.

**DoD:** `go test ./cmd/tmnc/ -race`; обратная совместимость: если в конфиге только `server = "..."`, поведение как сейчас.

### T3.4 `feat/probing` — anti-probing hardening и диагностика

**Зачем.** Сервер должен проходить активное зондирование неотличимо от сайта; владелец должен видеть, почему не работает (FR-11).

**Что сделать** (только `cmd/tmns/*` и `deploy/probe.sh`, `docs/`):
- Выровнять тайминги ответов на невалидный AUTH (не мгновенный ответ, не молчание 30 с — как обычный HTTP keep-alive).
- Ограничение частоты: не более N новых соединений с одного IP в минуту (как у nginx), ответ — обычный 429/сайт, не обрыв.
- Пробы из SDD §4: чужой SNI, пустой SNI, TLS 1.2, повтор AUTH, 20 соединений подряд, огромный POST, idle 15 с — все должны давать «как обычный сайт».
- `deploy/probe.sh`: 10 проб с ожидаемыми ответами и вердиктом PASS/FAIL, готовый к запуску на VPS.
- Диагностика FR-11: команда `tmns --selftest` или лог-строка с классификацией: какой слой подозревается (L1 порт/IP, L2 сигнатура, L3 TLS, L4 поведение), что сделано.
- Тесты: probe-тесты в Go (httptest + TLS-клиент) на каждый пункт из §4; rate-limit тест.

**DoD:** `go test ./cmd/tmns/ -race`; `bash -n deploy/probe.sh`; таблица «проба → ожидание → факт» в `docs/11-probing-results.md`.

## Конфликты файлов (важно при мерже)

| Файл | Кто правит |
|---|---|
| `cmd/tmnc/main.go` | `endpoint` (пул, список серверов) + `shaper` (обёртка conn в `dial`) |
| `cmd/tmnc/socks.go` | `route` (решение direct/tunnel) |
| `cmd/tmns/main.go`, `cmd/tmns/server.go` | `probing` + `shaper` (создание mux) |
| `mux/`, `proto/` | **никто** — не трогать |

Правило: если нужна правка в чужом файле — писать в отчёте «требуется правка X строки Y», а не лезть. Я разведу при мерже.
