# Т02 — TUN: пул буферов, батчинг кадров, ожидание кольца wintun, джиттер реконнекта

**Severity:** Medium (CPU/скорость на 1 Гбит/с, рывки при полном кольце)
**Репозиторий:** `E:/pet/tuman`
**Слой:** мост «IP-устройство ↔ mux-поток», обе стороны, плюс драйвер wintun

## Зачем

Три независимых дефекта в одном слое:

1. **Аллокация на каждый пакет.** `cmd/tmnc/tun.go:52-67` и
   `cmd/tmns/tun.go:43-59` создают `make([]byte, tun.MTU)` внутри цикла чтения
   устройства. На 1 Гбит/с при MTU 1398 это ~9000 пакетов/с ≈ 12.6 МБ/с мусора
   — GC-паузы каждые несколько секунд.
2. **Нет батчинга.** `toStream` делает один `st.Write` на пакет
   (`cmd/tmnc/tun.go:97-112`, `cmd/tmns/tun.go:89-98`): 9000 TLS-записей/с
   по 1410 байт вместо ~200 записей по 64 КиБ. Это не потолок, но это потолок
   `MaxPayload`-эффективности и лишние syscall'ы на обеих сторонах.
3. **Фиксированный сон при полном кольце.** `tun/tun_windows.go:76-80`:
   `ERROR_BUFFER_OVERFLOW` → `time.Sleep(2ms)` **на каждый** пакет. Одно
   усыпление стоит `1398×8/0.002 = 5.6 Мбит/с` пропускной способности, серия
   даёт рывки. Кольцо 4 МиБ (`tun/tun_windows.go:17-19`) на 20 Мбит/с не
   заполняется, поэтому в текущем симптоме это не участвует — но на гигабите
   это первое, что выстрелит.

Плюс мелочь в том же файле: реконнект IP-потока спит ровно секунду без
джиттера (`cmd/tmnc/tun.go:77`) — после рестарта сервера все клиенты бьют
одновременно.

## Что менять

### 1. Пул буферов чтения (обе стороны)

Пакетный `sync.Pool` рядом с мостом:

```go
var pktPool = sync.Pool{New: func() any { b := make([]byte, tun.MTU); return &b }}
```

`readDevice`: взять из пула, при ошибке — вернуть; при успехе передать
владение в канал срезом фиксированной ёмкости: `t.pkts <- (*bp)[:n:n]`.
`toStream` возвращает буфер в пул **после** копирования в батч.

### 2. Батчинг кадров в `toStream`

Локальный буфер `[8 * (2 + tun.MTU)]byte`, накопление пар
`u16 длина BE + пакет`, сброс одним `st.Write` при заполнении или когда канал
пуст. Формат провода **не меняется**: получатель читает 2+len в цикле, поток
байтовый, поэтому N пакетов в одной записи для него прозрачны. Заголовок mux
не трогаем — `st.Write` сам режет на `MaxPayload`.

Вынести сборку в тестируемую функцию, например:

```go
// tunBatch копит кадры «u16 длина + пакет» и сбрасывает их одним Write.
type tunBatch struct{ buf []byte } // Fill(p []byte) bool, Flush(w io.Writer) error
```

Тест гоняет её через `bytes.Buffer` (никакого устройства не нужно).

### 3. Ожидание кольца wintun вместо сна

`tun/tun_windows.go:76-80`: заменить `time.Sleep(2*time.Millisecond)` на
`windows.WaitForSingleObject(d.s.ReadWaitEvent(), 5)` — событие взводится,
когда в кольце освобождается место. Комментарий-`shortcut`:

```
// shortcut: ReadWaitEvent взводится и на приход пакета, и на освобождение места
// в кольце; на >1 Гбит/с проверить, нет ли пропущенных wakeup'ов, и при
// необходимости добавить короткий backoff.
```

### 4. Джиттер реконнекта IP-потока

`cmd/tmnc/tun.go:77`: `time.Sleep(time.Second + rand.N(time.Second))`
(`math/rand/v2`), чтобы после рестарта сервера потоки не приходили синхронно.

## Критерии приёмки

1. `TestTunBatchFraming` (новый, `cmd/tmnc`): 3 пакета по 200 Б → ровно один
   `Write` в `bytes.Buffer`, разбор обратно даёт те же 3 пакета в том же
   порядке; 9 пакетов → два `Write` (8 + 1), формат не поехал.
2. `TestTunBatchRejectsOversize`: пакет > MTU отбрасывается, батч не портится.
3. `BenchmarkTunReadLoop` (новый, с фейковым `tun.Device` — интерфейс уже есть
   в `tun/tun.go`): `0 allocs/op` на пакет после правки (текущий код даёт 1).
4. `GOOS=windows go build ./...` и `go test ./cmd/tmnc/ ./cmd/tmns/ -count=1`
   зелёные (wintun-код компилируется только под Windows — проверить сборкой,
   тесты на этой машине идут на windows/amd64, так что достаточно `go build`).
5. Полный прогон `go test ./... -count=1`.

## Риск

Средний: меняется владение буфером (пул). Опасность — вернуть буфер в пул,
пока он ещё читается (`toStream` пишет асинхронно). Правило: буфер возвращается
только после `copy` в батч и только в той горутине, которая его получила.
Батчинг по проводу безопасен: приёмник читает поток по 2+len.
