# TMN/2: видение, требования и план работ

Дата: 2026-11-02. Основание: аудит `docs/12-security-audit.md`, PRD `docs/02-prd.md`,
SDD `docs/03-system-design.md`, `docs/10-stage3-decomposition.md`.

## 1. Видение

Сегодня TMN/1 — быстрый туннель с сайтом-прикрытием, который снаружи выглядит как
**Go-клиент с наклейкой `h2`**: стоковый ClientHello (3 шифра, 11 расширений, без
GREASE), 4 TLS к одной паре (IP,SNI) за 13 мс, бинарный кадр первым байтом после
согласованного `h2`, адреса целей в логах сервера. Скорость у него есть (227 Мбит/с
на живой маршрут, 335 МБ/с mux на 32 потоках, 0 аллокаций на кадр), а вот обещание
«неотличим от браузера» не выполняется ни в одной части: ни отпечаток, ни профиль
соединений, ни логи.

TMN/2 — это тот же быстрый кадровый туннель, у которого:

1. **Снаружи нет ни одного признака, отличающего его от визита в браузере** —
   отпечаток Chrome, профиль соединений ≤2 на ендпоинт, ALPN соответствует
   содержимому, логи без целей.
2. **Внутри нет доверия ни одной из сторон по умолчанию** — обе доказывают знание
   ключа, реплей невозможен, нарушитель окна убивает только себя.
3. **Сбой одного компонента не убивает остальное** — поток не роняет сессию, сессия
   не роняет сервер, сервер не роняет процесс.

Целевой пользователь — 1–5 человек на своём VPS (G6 PRD), владелец сам себе админ.
Отсюда приоритет: не «фичи для рынка», а **отсутствие поводов заметить нас и
отсутствие способа уронить сервис**.

## 2. Требования TMN/2

Метки: **R** — обязательное для v2, **O** — желательное.

### Безопасность

| ID | Требование | Приёмка |
|---|---|---|
| R-SEC-1 | Сервер доказывает знание PSK в `AUTH_OK` (MAC + эхо nonce) | фейк-сервер без PSK не устанавливает сессию: `mux.New(IsClient:true)` возвращает ошибку |
| R-SEC-2 | Привязка AUTH не зависит от TLS-стека | AUTH проходит под `utls.HelloChrome_Auto` и под `crypto/tls` одинаково |
| R-SEC-3 | Реплей AUTH невозможен в пределах окна | повтор `(ts,nonce)` на другой сессии → `ErrAuth`; кэш один на сервер, под `-race` |
| R-SEC-4 | Egress ограничен политикой: никаких loopback/RFC1918/link-local/metadata | диал на `127.0.0.1`, `169.254.169.254`, `10.0.0.1`, `::1` отклоняется до соединения |
| R-SEC-5 | В логах нет SNI, адресов и URL целей | грепом по debug-логу потока не находится ни одного `host:port` цели |
| R-SEC-6 | Приёмное окно соблюдается принудительно | пир, заливший > окна, теряет сессию; RSS сервера не растёт |
| R-SEC-7 | Окно свежести `ts` не обходится переполнением | `ts = now ± 2^63` → `ErrAuth` |
| R-SEC-8 | Права PSK-файла проверяются (не-Windows) | файл 0644 → отказ на старте |

### Устойчивость

| ID | Требование | Приёмка |
|---|---|---|
| R-RES-1 | Ошибка уровня потока не роняет сессию | дубль OPEN, DATA после FIN, 257-й OPEN в accept → закрыт только поток |
| R-RES-2 | Исчерпание stream id не превращает туннель в зомби | `ErrExhausted` → пул переподключает сессию |
| R-RES-3 | `WU` с любой дельтой не вешает и не раздувает окно | `WU(2^31)`, `WU(2^32-1)` — окно в границах, `Write` не виснет |
| R-RES-4 | Флуд не выедает CPU до handshake | соединение сверх лимита закрывается до TLS; ошибка `Accept` не роняет процесс |
| R-RES-5 | Обрыв сразу после установления не даёт лавину | ≤2 реконнекта/с на ендпоинт при сервере, рвущем сразу |
| R-RES-6 | Восстановление после блипа ≤3 с (NFR-12) | сервер вернулся → 4 сессии за ≤3 с |
| R-RES-7 | `Close()` не виснет на conn без `io.Closer` | `Close()` возвращается < 3 с |
| R-RES-8 | relay не держит поток вечно | SOCKS-нога с idle > 300 с закрывается |

### Производительность и неотличимость

| ID | Требование | Приёмка |
|---|---|---|
| R-PERF-1 | Горячий путь остаётся zero-alloc | бенч `-benchmem`: аллокаций на кадр не больше, чем сейчас |
| R-PERF-2 | Mux не теряет скорость при контроле окна | `BenchmarkMuxThroughput` ≥ 600 МБ/с |
| R-PERF-3 | Отпечаток = браузер | JA3/JA4 совпадает с Chrome; ALPN соответствует первому байту |
| R-PERF-4 | Не более 2 TLS на ендпоинт | на одном ендпоинте при `conns=4` поднимается 2, не 4 |
| R-PERF-5 | Resumption включён | в hello присутствует ext 41, `DidResume=true` на втором коннекте |

## 3. AUTH v2 (R-SEC-1, R-SEC-2, R-SEC-3)

### Формат

```
AUTH     (клиент → сервер), 82 байта:
  ver      u16 = 2
  ts       u64  (unix, окно ±120 с, без модуля — сравнение в обе стороны)
  nonce    8    (случайный)
  clientPub 32  (X25519, эфемерный)
  tag      32   = HMAC-SHA256(psk, "TMN1-AUTH-V2" ‖ ver ‖ ts ‖ nonce ‖ clientPub)

AUTH_OK  (сервер → клиент), 74 байта:
  ver      u16 = 2
  nonce    8    (эхо из AUTH)
  serverPub 32  (X25519, эфемерный)
  tag      32   = HMAC-SHA256(psk, "TMN1-AUTH-OK-V2" ‖ clientPub ‖ serverPub ‖ ts ‖ nonce)

sessionKey = HKDF-SHA256(salt=psk, ikm=X25519(clientPriv, serverPub), info="TMN1-SESSION-V2", 32)
```

Всё фиксированной длины, big-endian, без negotiate: `ver != 2` → отказ (поверхности
downgrade нет, как и в v1).

### Почему ECDH вместо TLS-exporter

Exporter был выбран, чтобы привязать AUTH к конкретному TLS-соединению. Он это делает
корректно — но только на `crypto/tls`: браузерные ClientHello в uTLS включают
`renegotiation_info`, utls из него включает renegotiation, и exporter становится
недоступен (проверено, см. `12-security-audit.md` §5). Плюс exporter привязывает нас к
TLS, а на роадмапе QUIC — там своя обвязка.

X25519 внутри AUTH даёт то же свойство (сессионный ключ знают только двое) без
зависимости от транспорта и без доверия к TLS-стеку. Стоимость — одна пара ключей на
сессию (~50 мкс) и +32 байта в AUTH.

### Threat model

| Атака | До v2 | После v2 |
|---|---|---|
| MITM с доверенным CA читает трафик | видит цели и payload (S2) | получает `AUTH`, но не может ответить валидным `AUTH_OK` → клиент рвёт сессию до отправки целей |
| Реплей AUTH в пределах 120 с | невозможен (exporter), но и кэш мёртв | кэш на сервере + `ts` → `ErrAuth` |
| Реплей после 120 с | невозможен | невозможен (окно) |
| Подмена nonce/pub | n/a | тег ловит |
| Компрометация PSK | полный доступ | полный доступ (по-прежнему единственный секрет) |

Что v2 **не** решает: защиту от квантового противника (X25519 и HMAC — классика),
защиту от компрометации самого устройства клиента, сокрытие факта использования
туннеля от активного зонда, который знает протокол.

### Проверено (не теория)

`proto/auth.go` реализован и покрыт тестами, и дизайн проверен сквозным прогоном:
`uTLS` (HelloChrome_Auto / HelloFirefox_Auto / HelloSafari_Auto / HelloGolang) →
TLS 1.3 → AUTH v2 → AUTH_OK v2 → session key. Результат по всем четырём отпечаткам:

```
chrome   alpn="http/1.1" authok_verify=<nil> srv_err=<nil> key_match=true
firefox  alpn="http/1.1" authok_verify=<nil> srv_err=<nil> key_match=true
safari   alpn="http/1.1" authok_verify=<nil> srv_err=<nil> key_match=true
golang   alpn="http/1.1" authok_verify=<nil> srv_err=<nil> key_match=true
```

То есть браузерный отпечаток и взаимная аутентификация совместимы — чего нельзя было
сделать на TLS-exporter. Тесты `proto/auth_v2_test.go`: `TestAuthOKV2RequiresMAC`
(в т.ч. v1-подобный 12-байтовый AUTH_OK отвергается), `TestSessionKeyV2` (включая
low-order point), `TestAuthSkewOverflow` (доказывает, что старая формула давала
`d = -9223372036854775808` и пропускала метку), `TestReplayConcurrent` под `-race`.

### Миграция

Разрыв совместимости: старый клиент с новым сервером и наоборот не работают. Порядок:
сервер обновляется первым, но **не заменяет сетевой порт**, пока не обновлены клиенты —
на время перехода держим два listener'а (v1 на старом порту, v2 на новом), затем
v1 выключается. Бинарник v1 сохраняем для отката. В `docs/07-proto-v1-spec.md`
добавляется раздел «v2», старая спецификация остаётся как история.

## 6. Порядок и риски

Приоритет работ: S1 (OOM) → S3 (SSRF) → S4 (логи) → S2/S7 (AUTH v2 + uTLS) →
устойчивость клиента → всё остальное. Логика: сначала то, что превращает утечку ключа
или баг пира в компрометацию хоста; потом то, что видно снаружи; потом удобство.

Риски:

1. **Протокольный разрыв** (AUTH v2). Смягчение: двойной listener на время миграции +
   сохранённый v1-бинарь.
2. **Контроль окна против скорости** (R-PERF-2). Смягчение: проверка перед `push` в том
   же критическом участке, что уже берётся под `s.mu`; бенч до/после обязателен.
3. ~~uTLS из локального кеша~~ — **снято**: `utls v1.8.2` вендорен в `vendor/`
   (5.2 МБ), сборка идёт без сети, дефолт по-прежнему `crypto/tls`, uTLS
   включается только `fingerprint`.
4. **Правки четырёх агентов в одном рабочем дереве** без коммитов. Смягчение: файловые
   наборы не пересекаются, я проверяю каждую правку и гоняю полный `go test ./...`
   после сведения.
5. **Всё измерено на loopback.** Живой DPI, потери, смена сети — только на VPS.

## 7. Волна 1: что уже в дереве (проверено оркестратором)

| Фикс | Где | Чем доказано |
|---|---|---|
| приёмное окно: залив сверх окна валит сессию | `mux/mux.go` (`recvTotal`), `mux/stream.go` (`deliver`) | 8 МиБ в поток 8 МиБ → heap **+12 МиБ** вместо **+282 МиБ** |
| `WU(2^31)` не вешает поток | `mux/stream.go` | вычерпанное окно + `WU(2^31)`, законная `WU` будит `Write` |
| 300 OPEN не травят `AcceptStream` | `mux/mux.go` | после 300 OPEN `PING` жив, потоки отдаются |
| брошенные потоки возвращают conn-окно | `mux/mux.go` (`returnRecvWindow`) | 32 потока по 1 МиБ, затем 1 МиБ проходит за 5 с |
| `Close()` возвращается без `io.Closer` | `mux/mux.go` | `io.ReadWriter` без `Closer`, 5 с — не виснет |
| AUTH v2 подключён (аддитивно) | `mux/mux.go`, `client/`, `cmd/tmnc` (`auth_v2`) | 5 тестов: поток, совпадение ключа, v1-клиент, MITM без PSK, реплей между сессиями |
| `ReplayCache` общий на процесс | `mux.Config.Replay` | повторный `AUTH` отвергнут |
| адрес цели не утекает в лог | `cmd/tmns/server.go` | `169.254.169.254` не переживает в тексте ошибки |
| egress-политика (loopback/link-local/RFC1918) | `cmd/tmns/hardening.go` | живьём: `127.0.0.1`, `169.254.169.254`, `10.0.0.1` → `egress_denied` |
| лавина реконнектов | `client/pool.go` | 6 handshake за 4 с вместо 6189 за 3 с |
| восстановление после блипа | `client/health.go` | 511 мс (NFR-12 ≤ 3 с) |

Версия AUTH выбирается **по длине кадра** (`proto.AuthV2Len`), согласования нет —
старый клиент продолжает работать с новым сервером. Живьём: v1-бинарь `9db9287`
против нового сервера — 2.0 МБ за 0.97 с; `auth_v2=true` — 2.0 МБ за 0.95 с.

**Найдено при сведении (не в отчётах агентов):**

1. Агент сузил ALPN сервера до `["http/1.1"]`, а клиент просил `h2` — старый парк
   перестал подключаться (`handshake` падал на ALPN). Сервер: `http/1.1` первым,
   `h2` вторым; клиент предлагает `h2,http/1.1` (как браузер). В TLS 1.3 выбор едет
   в EncryptedExtensions и пассивному DPI не виден, поэтому запрет `h2` ничего не давал.
2. ~~Первый запрос после старта клиента обрывается~~ — **снято, дефект не наш**.
   Замер: 20 холодных запусков клиента по одному TLS-запросу → 2 отказа (10 %);
   база `9db9287` — 2 из 20; **без туннеля прямой `curl` — 1 из 12**. Временная
   сборка сервера с логированием ошибок копирования показала точную причину:
   `wsarecv: An existing connection was forcibly closed by the remote host` —
   RST от пограничного узла Cloudflare после ClientHello. Не tunnel, не mux,
   не клиент: так ведёт себя сеть этого хоста. Прогрев пула ничего не лечит и
   не нужен: сессия поднимается лениво на первом `DialContext` (~90 мс) и
   первый запрос не медленнее последующих (0.115 с против 0.153 с).

## 8. Волна 2: браузерный отпечаток (NFR-8) — в дереве

**Что сделано.** `client/utls.go`: `fingerprint = off|chrome|firefox|safari|golang`.
По умолчанию `off` — обычный `crypto/tls`, ничего не меняется. uTLS включается
только явным выбором; профиль живёт рядом с `auth_v2` и без него не собирается:
`New` отвергает `fingerprint` без `auth_v2`, потому что uTLS держит renegotiation
включённым и Go на этом отказывает в `ExportKeyingMaterial` — привязка к каналу
остаётся только через X25519-MAC v2.

**Зависимость.** `refraction-networking/utls v1.8.2` вендорен в `vendor/` (5.2 МБ):
сборка не требует сети, `go build ./...` на VPS работает без прокси. Политика
«go.mod без внешних зависимостей» умерла осознанно: без uTLS отпечаток не
подделать, а руками писать ClientHello с GREASE и перестановкой расширений —
это fork TLS-стека.

**Найдено при сведении (проверено мной, не агентами):** `mux.New` требовал
`len(cfg.Exporter) == 32` **всегда**, то есть любой транспорт без TLS-exporter
(uTLS) падал в `ErrHandshake` до первого кадра — и на клиенте, и на сервере,
с одинаковым текстом. Условие стало `!cfg.AuthV2 && len(cfg.Exporter) != 32`:
exporter обязателен только тому, кто может говорить AUTH v1.

**Замеры.**

| Проверка | Результат |
|---|---|
| hello Chrome на проводе | первые три не-GREASE шифра `1301,1302,1303`, GREASE `0xEAEA` впереди, ALPN `h2` первым, SNI есть — тест `TestFingerprintBrowsers` |
| firefox / safari | сессия поднимается, эхо возвращается, hello с ≥2 кривыми и SNI |
| uTLS ≠ Go | списки шифров расходятся (`TestFingerprintDiffersFromGo`) |
| `fingerprint` без `auth_v2` | ошибка конфига, а не разрыв на первом dial |
| record layer, локально | tls 1247 МБ/с, utls 1238 МБ/с — 0.7 %, в пределах шума |
| живьём через туннель | 2 МБ за 0.93 с, 5 МБ за 4.0 с (потолок маршрута, как у v1-базы) |

**Что не доказано.** JA3/JA4 нашего hello не сверялся с живым Chrome: Chrome на
хосте не запускался, эталон — сам uTLS. Проверка «не палимся» на реальном ТСПУ
по-прежнему не сделана: все замеры на loopback и через один и тот же маршрут.

## 9. Волна 3: DoH внутри туннеля (FR-9) — в дереве

**Дыра.** Сервер диалел цель по имени системным резолвером, то есть спрашивал
DNS провайдера VPS открытым UDP/53. Провайдер видел каждое имя, которое открывает
клиент — весь смысл туннеля терялся на последнем участке.

**Что сделано.** `cmd/tmns/doh.go`: резолвер поверх DoH (RFC 8484, POST
`application/dns-message`), ключ конфига `dns = "https://…/dns-query"`. Пусто или
`system` — прежнее поведение, поэтому существующие установки не меняются.
Спрашиваются A и AAAA параллельно, кеш по TTL (границы 60 с … 1 ч: нулевой TTL
иначе означает HTTPS на каждый сокет, суточный переживает смену A-записи).
CNAME-цепочка проходится до конца — адреса стоят после неё.

**Отката на системный резолвер нет намеренно**: молчаливый fallback вернул бы
утечку, оставив оператора в уверенности, что DoH работает. Отказ виден как
`egress err=dns` и поток закрывается.

**Найдено при проверке:** AAAA обычно приходит раньше A, и «первый адрес» на
VPS без IPv6 — недостижимый. Адреса сортируются: IPv4 первым.

**Замеры.**

| Проверка | Результат |
|---|---|
| живой DoH (`https://1.1.1.1/dns-query`) через туннель | example.com 577 байт, 2 МБ за 0.94 с — как без DoH (0.93), кеш снимает накладные |
| мёртвый DoH-эндпоинт | запрос падает за 4 мс, `err=dns`, системный резолвер не подхватывает |
| кеш | 5 обращений к одному имени = 2 запроса к DoH (A+AAAA один раз) |
| IP-литерал | в DoH не уходит вовсе |

**Что не проверено.** DoH на самом VPS: с этого хоста 1.1.1.1 отдаёт разовые RST
(та же сетевая особенность, что и с example.com), поэтому живой прогон сделан
через тот же маршрут, а не с хельсинкского сервера. Кеш не ограничен по размеру —
при десятках тысяч уникальных имён это медленный рост карты; граница с TTL.

## 10. Волна 4: UDP-релей (FR-6)

**Дыра.** `UDP ASSOCIATE` отвечал `repNoCommand`: голос, QUIC и системный
резолвер шли мимо туннеля. Приложение, не умеющее TCP-DNS, обходило туннель
целиком — и провайдер видел и имена, и адреса.

**Форма.** Датаграммы едут в обычном mux-потоке, помеченном `proto.FlagUDP` на
OPEN; внутри — «u16 длина + данные». Данные остаются потоком байт, поэтому
фрагментация, окно и шейпер работают без изменений, а старый TCP-путь не тронут
вовсе. Цена — по потоку на цель: у приложения их единицы (резолвер, пара CDN),
карта живёт на ассоциацию, потолок 64 цели.

**Что пришлось решить.**

- *Политика.* UDP-цель проходит те же `egressAllowed` и DoH, что TCP; маршрутная
  таблица клиента тоже применяется на каждую цель — иначе `block` обходится
  одной датаграммой.
- *Привязка к источнику.* Отвечаем только тому адресу, который первым прислал
  датаграмму: иначе локальный UDP-резолвер и egress-канал достались бы любому
  процессу на хосте.
- *Фрагменты.* `FRAG≠0` отбрасывается по RFC, а не склеивается: склейка требует
  таймеров и памяти на поток, а приложения уже умеют в MTU.
- *Потолок.* 8 КиБ на датаграмму. Сервер считает нарушением формата и рвёт
  поток, но не сессию — проверено `TestTunnelUDPTooBig`.

**Замеры.** Живой DNS через туннель: 46–53 мс, `rcode=0`, 2 ответа в Answer,
три запроса подряд. TCP через тот же туннель после UDP: 577 байт за 0.15 с —
регрессии нет.

**Что не проверено.** Голос (RTP) и QUIC на реальном маршруте: для голоса нужен
MTU и потеря пакетов, для QUIC — что релей не ломает congestion feedback.
Проверено только, что датаграмма доходит и возвращается.

## 11. Волна 5: TUN (FR-1)

**Дыра.** Клиент умел только SOCKS5: приложение без его поддержки шло мимо
туннеля целиком.

**Форма.** L3-устройство на обоих концах и один mux-поток с `proto.FlagIP`,
кадры «u16 длина + IP-пакет». TCP, UDP, ICMP, окна и ретрансмиты делает стек
ядра — как в WireGuard. Своего userspace-стека нет намеренно: он тянет NAT,
таймеры и половину gVisor, а даёт то же самое.

**Что пришлось решить.**

- *MTU 1398, а не 1400.* Максимальная нагрузка кадра — 1400, длина кадра — 2
  байта. С MTU 1400 каждый пакет распадался на два DATA-кадра, второй почти
  пустой: двойное число кадров на ровном месте.
- *Backpressure вместо очереди.* Сначала пакеты складывались в Go-канал с
  `default: drop`. Под нагрузкой терялось **97 %** (5 МБ из 200). Канал убран:
  блокирующая запись останавливает чтение устройства, буфером служит кольцо
  драйвера на 4 МиБ. Стало 144 из 150 МБ.
- *Один владелец устройства на сервере.* Устройство одно на процесс, поэтому
  второй IP-поток получает отказ: иначе два клиента делят одно кольцо и теряют
  пакеты друг друга без диагностики.
- *Пустой payload в OPEN.* Найдено на этом шаге: `reserve(max=0)` ждал кредит
  окна вечно, поэтому поток без адресного блока (IP, FIN) не открывался вовсе.
  Починено в корне — кадр без нагрузки окно не тратит.
- *Маршруты не трогаем.* `default` через устройство увёл бы в него соединение с
  самим сервером. Обходной маршрут и `MASQUERADE` — деплой, не код.

**Замеры** (Windows 11, Wintun 0.14, оба конца на одной машине).

| Проверка | Значение |
|---|---|
| ICMP через туннель, 10×1328 Б | 13280 Б из 13280, потери 0 |
| UDP 1398 Б, 150 МБ, 2 потока | 3.2 Гбит/с предложено, 144 МБ доставлено (4 % — sender) |
| Перезапуск процесса | orphan-адаптер удалён драйвером, tunnel поднялся |
| Пакет больше MTU | проходит (ядро фрагментирует), мост не рвётся |

**Что не проверено.** TCP-производительность через TUN на реальном маршруте:
на одной машине адрес сервера локальный, и ядро замыкает трафик на loopback, не
доходя до устройства (первый замер «27 Гбит/с» был именно этим артефактом и
отброшен — проверять надо счётчиками адаптера). Linux-устройство собрано, но не
запускалось: на этом хосте нет `/dev/net/tun`. Split-tunnel по правилам в TUN не
работает — только маршрутами ОС.
