# Т01 — `mux.Stream.Read`: дренаж подряд идущих чанков

**Severity:** High (пропускная способность релея, CPU на 100+ Мбит/с)
**Репозиторий:** `E:/pet/tuman`
**Слой:** мультиплексор, приём

## Зачем

`Stream.Read` отдаёт не более одного чанка (4 КиБ) за вызов. Все релеи
(`cmd/tmnc/socks.go`, `cmd/tmns/tun.go`, `cmd/tmnc/tun.go`) читают поток
буфером 32 КиБ и получают 4 КиБ, то есть работают «по 4 КиБ»:

- один `Write` в локальный сокет на каждые 4 КиБ (`cmd/tmnc/socks.go:357-360`),
  и на каждую такую запись — `SetWriteDeadline` → две операции сетевого
  поллера вместо одной;
- на 1 Гбит/с это ~30 000 итераций/с и столько же сбросов дедлайна.

Пропускная способность одного потока при этом не упирается (замерено 635 МБ/с
через `io.CopyBuffer`), но на 8–16 параллельных потоках растёт CPU и джиттер —
ровно то, что видно как «лаги» под нагрузкой, а не как потолок.

## Механика

`mux/stream.go:60-100`: `Read` берёт `st.rq[st.rhead]`, копирует сколько влезло
в `p`, при исчерпании чанка возвращает его в пул и **сразу** возвращает `n`.
Следующий чанк уже лежит в `st.rq`, но вызов его не трогает — лишний проход
через `select`/`rwake` и лишний системный вызов у вызывающего.

## Что менять

Файл: `mux/stream.go`, только тело `Read` (плюс, при необходимости, мелкий
локальный хелпер рядом).

1. Внутри того же захвата `st.rmu` копировать **подряд идущие** чанки, пока
   не заполнится `p` или не кончится `st.rq`.
2. Каждый полностью прочитанный чанк — в `done []*chunkBuf` (не в пул сразу:
   `pChunk.Put` под `rmu` держит пул дольше, чем нужно).
3. Вернуть все `done` в пул **после** `st.rmu.Unlock()`, до `consumed`.
4. `consumed(n, drained)` вызывать один раз на вызов `Read` с суммарным `n`;
   `drained` = очередь пуста после дренажа.
5. `st.compact()` — один раз, если был хоть один полностью прочитанный чанк.
6. Дедлайн/`rerr`/`rwake` — без изменений, порядок проверок сохранить.

Инварианты, которые нельзя сломать:
- один `*chunkBuf` возвращается в `pChunk` ровно один раз (двойной `Put`
  отравит пул мусором — это тихая порча данных);
- `recvPending`/`recvTotal`/`recvUsed`/`connUsed` учитываются на каждый
  прочитанный байт, как сейчас (иначе окно утечёт и поток встанет);
- `Read(0)` по-прежнему не трогает очередь.

## Границы

Трогать можно: `mux/stream.go`, `mux/stream_test.go`.
Не трогать: `mux/mux.go`, `proto/`, `client/`, `cmd/` — это чужие задачи.

## Критерии приёмки

Тесты (новые, в `mux/stream_test.go`):

1. `TestReadDrainsConsecutiveChunks`: отправитель пишет 3 кадра по 1400 Б,
   `Read` буфером 8 КиБ возвращает `n == 4200` за один вызов.
2. `TestReadPartialAcrossChunks`: буфер 1000 Б → `Read` возвращает 1000, а
   следующий `Read` — 400 (граница чанка не теряется).
3. `TestReadByteExact`: 1 МиБ случайных байт через поток, побайтовая сверка
   с источником (ловит и двойной `Put`, и потерю байта на стыке).
4. Существующие `fc_test.go`/`stream_test.go` (окна, FIN, дедлайны) — зелёные
   без правок.

Замеры:

```
go test -run XXX -bench 'BenchmarkRelay' -benchtime 3x ./mux/
```
База до правки: `RelayCopy32K` 635.54 MB/s / 621 allocs/op,
`RelayCopyPlain` 667.28 MB/s / 591 allocs/op. После правки — не хуже по MB/s
и без роста allocs/op (файл `mux/zz_baseline_test.go` — временный, его
не трогать, он нужен оркестратору для сверки).

Полный прогон: `go test ./mux/ -count=1`, затем `go test ./... -count=1`.

## Риск

Средний: меняется ядро приёма. Основная опасность — двойной возврат в пул и
потеря учёта окна; оба ловятся тестами 1–4 и `-race`.
